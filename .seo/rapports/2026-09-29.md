## Moyen technique utilisé et note opérationnelle

Connecteur MCP GitHub (`mcp__remote-devices__GitHub_MCP_Server__JS___*`) utilisé pour toutes les opérations de lecture et d'écriture sur le dépôt ce run. Bash local utilisé en complément pour le décodage base64 des fichiers `.seo/*` déjà récupérés par le connecteur (lecture seule, aucune écriture sur le dépôt par ce biais). WebSearch et WebFetch utilisés pour la veille concurrentielle et la vérification technique du site live (`robots.txt`, `sitemap.xml`).

Précision utile sur le mécanisme technique, observée ce run : les outils GitHub (`mcp__remote-devices__GitHub_MCP_Server__JS___*`) ne sont pas un connecteur cloud direct mais un serveur MCP local (« GitHub MCP Server (JS) ») qui tourne sur l'ordinateur Windows de l'utilisateur, exposé à cette session via le pont `remote-devices`. En milieu de run, la connexion au pont a été brièvement interrompue (154 outils déchargés d'un coup, `get_device_info` a échoué une première fois avant de réussir au second essai). Ceci explique rétroactivement les alertes outillage répétées des runs précédents (erreurs de montage Windows, « VM service not running », etc.) : l'écriture sur ce dépôt dépend d'une machine et d'une application de bureau connectées côté utilisateur, une dépendance fragile pour une tâche planifiée censée s'exécuter sans surveillance. Ce run n'a subi aucune perte de données grâce au nouvel essai automatique, mais le risque qu'un run futur échoue complètement à committer (dépôt inaccessible faute de connexion du pont, sans repli cloud direct) reste entier et mérite d'être signalé à l'utilisateur : un token GitHub direct utilisable depuis le bac à sable cloud de la session, indépendant de la connexion au bureau, sécuriterait la routine.
